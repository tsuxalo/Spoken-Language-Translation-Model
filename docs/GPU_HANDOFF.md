# 1. What this experiment is testing

The main research question is:

> **Can Hausa → English machine translation be made more robust to the actual errors produced by an upstream Hausa ASR system?**

## Why we are doing this experiment

This experiment is the scaled-up follow-up to an earlier **25-example pilot** we already ran.

In that pilot, we compared Hausa → English translation when NLLB received:

```text
1. Gold Hausa transcripts
2. Hausa transcripts generated by our Whisper ASR system
```

The pilot showed a large drop in downstream translation quality when gold Hausa was replaced by ASR-generated Hausa. In the earlier smoke test, NLLB went from roughly:

```text
Gold Hausa:
BLEU ≈ 24.45
chrF++ ≈ 49.95

Whisper ASR Hausa:
BLEU ≈ 8.03
chrF++ ≈ 33.37
```

The same pilot also found that higher ASR word error rate tended to correspond to worse translation quality.

That gave us an important **preliminary observation**:

> The cascade appears to suffer substantial error propagation from ASR into machine translation.

However, **25 examples are far too few to make a strong capstone-level claim**. They are useful for generating a hypothesis and verifying that the pipeline works, but they are not enough for robust statistical conclusions.

The final GPU experiment therefore asks a more rigorous follow-up question:

> **If ASR errors are the problem, can we explicitly train the MT model to become more robust to the actual error distribution produced by our Hausa ASR system?**

That is why we create the three controlled LoRA conditions:

```text
CLEAN:
gold Hausa → English

NOISY:
Whisper-generated Hausa → English

MIXED:
50% gold Hausa + 50% Whisper-generated Hausa → English
```

All three models are then tested on the same held-out Whisper-generated Hausa from NaijaS2ST `dev`.

The progression of the project is therefore:

```text
25-example pilot
      ↓
Observed large clean-vs-ASR translation degradation
      ↓
Observed preliminary WER → translation-quality relationship
      ↓
Hypothesis:
MT is mismatched to the noisy ASR distribution
      ↓
Large-scale controlled clean / noisy / mixed experiment
      ↓
Held-out evaluation + confidence intervals + error analysis
```

So the purpose of the large GPU experiment is **not simply to repeat the 25-sample test with more examples**.

It does three additional things:

1. **Validates the original error-propagation observation at proper scale.**
2. **Tests a proposed intervention** — error-aware MT adaptation — rather than merely measuring the problem.
3. **Provides statistically defensible evidence** using held-out evaluation, BLEU, chrF++, SSA-COMET, bootstrap confidence intervals, and ASR error analysis.

The 25-example result should therefore be described in the final report as a **pilot / exploratory experiment that motivated the final hypothesis**, while the large GPU experiment is the main confirmatory capstone study.

---

The project uses a cascaded speech-translation pipeline:

```text
Hausa speech
    ↓
Hausa ASR
    ↓
machine-generated Hausa text
    ↓
Hausa → English MT
    ↓
English translation
```

The problem is that MT models are usually trained on relatively clean written Hausa, while at inference time they receive noisy ASR output.

This experiment tests whether adapting the MT model to that real ASR-error distribution improves downstream speech translation.

The primary controlled comparison is:

| System | MT training input | Final evaluation input |
|---|---|---|
| NLLB baseline | original pretrained model | Whisper ASR Hausa |
| AfriNLLB baseline | original model | Whisper ASR Hausa |
| Clean LoRA | gold Hausa | Whisper ASR Hausa |
| Noisy LoRA | Whisper-generated Hausa | Whisper ASR Hausa |
| Mixed LoRA | 50% gold + 50% Whisper-generated Hausa | Whisper ASR Hausa |

The **clean / noisy / mixed** conditions are exposure-matched so all three see the same number of training examples.

# 2. Important experimental rules

Please follow these rules exactly.

1. **Do not run expensive training unless CUDA is working.**
2. Use NaijaS2ST `train` only for training and internal validation.
3. Keep NaijaS2ST `dev` untouched until all three LoRA models are trained.
4. Use the same random seed for all controlled conditions: `42`.
5. Use the same training hyperparameters for clean / noisy / mixed.
6. If GPU memory forces a batch-size change, use the same effective batch size for all three models.
7. Do not install COMET before model training unless necessary. COMET can constrain/downgrade `transformers`.
8. Save all final metadata and results.
9. Do not commit large generated manifests, model checkpoints, or adapter weights unless the team explicitly agrees to do so.
10. After the research split is created, perform the required sanity checks below. If they pass, continue directly into the three LoRA training runs. Only stop and contact the team if the checks fail or the dataset statistics look clearly abnormal.

# 31. Troubleshooting

## CUDA is False

Run:

```powershell
python -c "import torch; print(torch.__version__); print(torch.version.cuda); print(torch.cuda.is_available())"
```

If it remains false, the environment has CPU-only PyTorch or cannot access the NVIDIA driver.

**Do not begin training until this is fixed.**

---

## `nvidia-smi` does not work

The NVIDIA driver is unavailable to the environment.

Fix the GPU/driver/cluster configuration first.

---

## Out of memory during LoRA training

Use for all three models:

```text
--batch-size 1
--gradient-accumulation 8
--gradient-checkpointing
```

---

## Out of memory during evaluation

Use:

```text
--batch-size 1
```

---

## Out of memory during COMET

Use:

```text
--comet-batch-size 1
```

---

## Hugging Face rate-limit warning

Log in with a Hugging Face token if available:

```powershell
huggingface-cli login
```

or use the currently supported Hugging Face authentication command for the environment.

---

## Split reports overlap

If either:

```text
alignment_overlap > 0
```

or:

```text
text_pair_overlap > 0
```

**do not train.**

Send the split output back for investigation.

---

## A command fails after COMET installation

COMET can alter dependency versions.

That is why COMET should ideally run in `.venv-analysis`, separately from `.venv-gpu`.

Do not reinstall/downgrade the training environment after the models have begun training unless absolutely necessary.

# 32. Experiment stopping points

### Stop Point 1
If CUDA preflight fails.

### Stop Point 2
After `make_research_splits.py`, **only if the sanity checks fail**.

If `alignment_overlap = 0`, `text_pair_overlap = 0`, the row counts are sensible, and the training preflight passes, continue directly into LoRA training.

### Stop Point 3
If any of clean/noisy/mixed uses different data counts or unintentionally different hyperparameters.

### Stop Point 4
If the final dev set was accidentally used for training or model selection.

Tell the team before continuing so the evaluation protocol can be corrected.

---

# 33. Main scientific interpretation

The experiment is designed so that several outcomes remain meaningful.

### If Mixed wins

Evidence suggests retaining clean-text exposure while adapting to empirical ASR noise improves robustness.

### If Noisy wins

Direct adaptation to the actual ASR-error distribution appears most useful.

### If Clean wins

The gain may come mostly from Hausa-domain adaptation rather than explicit noise robustness.

### If none beat NLLB

That is still informative: downstream MT adaptation may not be sufficient to recover performance lost through ASR errors, suggesting that better ASR or more integrated speech-translation modeling is needed.

Do not change the experiment simply because an early result is disappointing.

# 34. Short version

The required core pipeline is:

```text
1. Pull karun/final-capstone-benchmark
2. Verify CUDA=True
3. Run gpu_preflight.py
4. Build full NaijaS2ST train alignments
5. Generate Whisper ASR outputs for train
6. Create leakage-resistant train/validation split
7. Sanity-check split; continue if it passes
8. Train clean LoRA
9. Train noisy LoRA
10. Train mixed LoRA
11. Generate untouched dev Whisper outputs
12. Evaluate NLLB + AfriNLLB + clean/noisy/mixed
13. Run gold-transcript oracle
14. Save environment/GPU/revision metadata
15. Run bootstrap + BLEU + chrF++ + SSA-COMET analysis
16. Return results to the team
```

The **required study is complete after Step 15**.

Omnilingual-ASR and NLLB-3.3B are optional strong baselines if there is enough GPU time.
